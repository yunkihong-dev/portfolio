    왜 만들었나

    대부분의 금융 서비스는 소비 내역과 통계를 보여주지만, 소비의 원인과 위험도에 대한 해석이 없고 관리가 단순 확인에 그쳐 개선으로 이어지지 않습니다. 개인별 소비 맥락을 반영한 안내가 필요하다고 판단해, 소비 데이터를 분석해 월간 리포트·카드 추천·AI 소비 상담을 제공하는 서비스를 만들었습니다.

    맡은 일

    Product Lead

    • 요구사항 분석, 기능 기획, 일정 관리
    • 기술 의사결정 (배치 도입, DB 이중화, 온프레미스 LLM)

    Backend

    • API 스펙 제작 · Swagger 문서화
    • DB 설계
    • 월말 리포트 점수 로직 (메인 로직)
    • Redis 캐싱 (Cache-Aside + Cache Evict)
    • 부하 테스트 이후 Spring Batch 도입

    Infra · CI/CD

    • VMware ESXi 기반 프라이빗 클라우드 구축 기여 (vCenter · 리소스 풀 · pfSense)
    • GitHub Actions 기반 DevSecOps 파이프라인
    • MySQL Master-Worker 이중화 (HAProxy · Keepalived)

    Frontend · Test

    • 소비내역(캘린더) 화면 · 소비일기 화면
    • 부하 테스트 시나리오 구성 및 실행

    왜 Spring Batch였나

    월말 리포트 점수는 한 달치 소비 데이터로 한 번 계산하면 그 달 안에서는 바뀌지 않습니다. 그런데 기존 구조는 사용자가 리포트를 열 때마다 같은 집계 쿼리를 다시 실행했고, 월말에 요청이 몰리면 실시간 API와 DB 커넥션을 두고 경합했습니다(아래 트러블슈팅 01). 커넥션 풀을 늘리거나 쿼리를 튜닝해도 '요청마다 계산한다'는 구조가 그대로면 사용자가 늘 때 같은 문제가 반복된다고 판단해, 계산 시점을 요청에서 떼어내기로 했습니다.

    요청 시 계산

    리포트 API 호출마다 소비 데이터를 조회해 점수 계산

    • 항상 최신 데이터 반영
    • 구현이 단순함
    • 같은 집계 쿼리가 요청마다 반복
    • 월말에 요청이 몰리면 커넥션 고갈 · 데이터 누락

    배치 사전 집계 최종 채택

    사용자가 적은 새벽에 한 번 계산해 저장, API는 결과만 조회

    • 실시간 API와 집계 작업의 자원 분리
    • 회원당 계산은 월 1회로 끝남
    • API 응답이 단순 조회 수준으로 짧아짐
    • 배치 주기만큼 반영이 늦음 (월 1회 리포트라 영향 없음)

    단순 스케줄러 대신 Spring Batch를 고른 이유

    • 청크 단위 트랜잭션 — 전체 회원을 한 트랜잭션으로 묶지 않고 10건씩 커밋해 커넥션을 오래 잡지 않고, 오류가 나도 해당 청크만 롤백됩니다.
    • 건별 결과 구분 — 목표가 없는 회원은 SKIPPED, 계산 오류는 FAILED로 나눠 한 명의 문제가 전체 결과를 가리지 않게 했습니다.
    • 실행 이력 관리 — JobRepository에 Job·Step 실행 상태가 남아 언제 돌았고 몇 건을 처리했는지 추적할 수 있습니다.
    • 역할 분리 — 대상 조회(Reader), 점수 계산(Processor), 결과 기록(Writer)을 나눠 단계별로 고치고 테스트하기 쉽습니다.
    • 멀티스레드 Step — 코드 변경 없이 설정으로 Step을 병렬 처리해 처리 시간을 줄일 수 있습니다.

    어떻게 구현했나 — 월말 리포트 배치

    매일 02:00 KST 스케줄러 트리거월말이 아니면 종료, 월말이면 JobLauncher로 calculateGoalScoreJob 실행. Step은 chunk size 10, 멀티스레드.
    READ — 대상 조회휴면 회원까지 계산하지 않도록 최근 3개월 내 로그인한 활성 회원만 List<Member>로 가져옵니다.
    PROCESS — 점수 산정당월 목표가 없으면 SKIPPED. 있으면 GoalService가 소비 데이터(총액·일별·필수여부)를 조회해 달성·안정성·비율·연속성 4개 점수를 계산하고 UPDATE.
    WRITE — 결과 집계SUCCESS / SKIPPED / FAILED 카운트를 MeterRegistry 메트릭으로 기록하고 배치 결과를 로깅. Grafana에서 실행 결과를 확인합니다.
    API — 결과만 조회리포트 API는 배치가 저장한 점수를 읽기만 합니다. 응답 시간 약 2s → 200ms.

    DB 이중화

    Master는 쓰기, Worker는 읽기를 맡고 실시간 복제로 동기화합니다. 한쪽에 장애가 나도 나머지가 즉시 역할을 이어받아 서비스가 끊기지 않고, 읽기 부하를 나눠 전체 DB 성능을 높였습니다. HAProxy와 Keepalived로 LB 자체도 이중화했습니다.

    02WireGuard 구성 후 가상머신 간 통신 전면 단절

    배경
    교육장에는 공인 IP가 하나뿐이라, 여러 팀이 같은 공동 인프라에서 동시에 AWS와 통신할 수 있도록 WireGuard 기반 VPN 터널을 구성했습니다.
    증상
    구성을 마친 뒤 특정 물리 서버의 모든 클러스터에서 가상머신에 접근할 수 없게 됐고, 여러 팀의 프로젝트 일정에 영향을 줄 수 있는 상황이었습니다.
    원인
    가상머신 상태와 내부 네트워크 설정에는 이상이 없어 외부와 연결되는 지점을 의심했고, 방화벽·VPN 설정을 정상 동작하는 팀의 구성과 하나씩 비교했습니다. 그 결과 WireGuard AllowedIPs가 172.16.0.0/16 대역 전체로 잡혀 내부 트래픽까지 VPN 터널로 라우팅되고 있었습니다.
    해결
    VPN을 비활성화해도 통신이 돌아오지 않아, 기존 터널 설정을 제거하고 라우팅 상태를 다시 확인했습니다. 터널링 대역을 필요한 범위로 좁혀 내부 네트워크가 VPN을 거치지 않도록 재구성한 뒤, 가상머신 간 통신을 직접 검증했습니다.
    이후
    관련 팀원과 원인을 함께 분석해 회고 문서로 남기고, 라우팅 변경 전 파급 범위를 미리 검토하는 절차를 만들었습니다.

    03퍼블릭 환경에서만 서비스 기동 실패

    증상

    • 최적화된 응답 성능

    • 데이터 정합성 완벽 보장

    2023.08 · 출근부 MVPIP 기반 출퇴근 기록과 사용자 관리만 있는 웹 출석부를 혼자 기획·개발해 운영 시작. 지각비 정산 자동화.
