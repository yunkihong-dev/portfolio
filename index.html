How I work

일하는 방식

로그를 끝까지 읽는다

같은 이미지가 프라이빗에선 잘 뜨는데 퍼블릭에서만 안 뜬 적이 있습니다. 코드는 그대로였으니 환경 문제겠다 싶어 CI 로그와 기동 로그를 처음부터 하나씩 따라갔고, 퍼블릭 쪽에서 환경변수가 빠져 있던 걸 찾아 파이프라인을 고쳤습니다.

구조부터 의심한다

월말 리포트를 만드는 작업이 실시간 API와 같은 서버에서 돌면서 CPU가 70%를 넘고 데이터도 빠졌습니다. 쿼리를 손보는 대신 Spring Batch로 배치를 아예 떼어냈더니 유실이 사라지고 CPU는 57.9%까지 내려갔습니다.

막히면 바로 말한다

혼자 붙잡고 있다가 대응이 늦어진 적이 있습니다. 그 뒤로는 어느 정도 막히면 팀 채널에 먼저 올립니다. 그렇게 같이 보고 30분 만에 푼 문제도 있습니다.

왜 만들었나

대부분의 금융 서비스는 소비 내역과 통계를 보여주지만, 소비의 원인과 위험도에 대한 해석이 없고 관리가 단순 확인에 그쳐 개선으로 이어지지 않습니다. 개인별 소비 맥락을 반영한 안내가 필요하다고 판단해, 소비 데이터를 분석해 월간 리포트·카드 추천·AI 소비 상담을 제공하는 서비스를 만들었습니다.

월말 리포트를 실시간 API에서 떼어내기

월말 리포트 생성이 실시간 API 처리와 동시에 돌면서 서버 리소스 경합이 생겼습니다. 대량 데이터를 처리할 때 DB 커넥션이 부족해 일부 데이터가 누락되고 CPU 사용률이 70%를 넘었습니다. 온프레미스 부하 테스트로 병목을 확인한 뒤, Spring Batch로 배치 작업을 완전히 분리하고 청크 방식으로 메모리를 쓰도록 바꿨습니다. 데이터 유실 0건, CPU 부하 13% 감소.

DB를 Master-Worker로 이중화

Master는 쓰기, Worker는 읽기를 맡고 실시간 복제로 동기화합니다. 한쪽에 장애가 나도 나머지가 즉시 역할을 이어받아 서비스가 끊기지 않고, 읽기 부하를 나눠 전체 DB 성능을 높였습니다. HAProxy와 Keepalived로 LB 자체도 이중화했습니다.

매일 02:00 KST 스케줄러 트리거월말이 아니면 종료, 월말이면 calculateGoalScoreJob 실행. Step은 chunk size 10, 멀티스레드.
READ — 대상 조회최근 3개월 내 로그인한 활성 회원만 List<Member>로 가져옵니다.
PROCESS — 점수 산정당월 목표가 없으면 SKIPPED. 있으면 소비 데이터(총액·일별·필수여부)를 조회해 달성·안정성·비율·연속성 4개 점수를 계산하고 UPDATE.
WRITE — 결과 집계SUCCESS / SKIPPED / FAILED 카운트를 MeterRegistry 메트릭으로 기록하고 배치 결과를 로깅.

왜 만들었나

금융업계에는 3-Tier 레거시 구조가 많고, 특정 기능에 트래픽이 몰리면 그 지점에서 장애가 납니다. 병목이 생기는 지점을 '이자 지금 받기' 기능으로 채택해 시나리오를 만들고, 다양한 Redis 캐싱 전략으로 성능을 얼마나 끌어올릴 수 있는지 실측하기로 했습니다.

캐싱 전략 비교와 선택

금융 서비스는 데이터 정합성과 서비스 연속성이 중요한 환경이라 읽기·쓰기 전략을 따로 비교했습니다. 읽기는 Redis 장애 시에도 DB로 서비스를 이어갈 수 있는 Cache-Aside를 채택했고, 쓰기는 두 전략을 모두 구현해 성능·정합성·구현 복잡도를 정량 비교했습니다.

Cache Update

DB 갱신 직후 계산된 이자값(0)을 Redis에 즉시 갱신

  • 일관된 캐시 히트율 유지
  • 최적화된 응답 성능
  • 동시성 제어를 위한 분산락 필수
  • Evict에 비해 낮은 데이터 정합성

Cache Evict 최종 채택

이자 수령 시 캐시 즉시 삭제, 다음 조회 때 DB에서 다시 적재

  • 구현 복잡도 최소화
  • 데이터 정합성 완벽 보장
  • 레이스 컨디션 위험 제거
  • 삭제 후 첫 조회 시 DB 부하
  • 일시적 응답 지연 가능
